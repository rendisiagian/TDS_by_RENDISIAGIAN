Three standalone HTML pages form the UI layer with no build step: `dashboard_vatin.html` is the primary register offering server-side paginated filtering, inline edit of branch/invoice/date, multi-PDF upload via pdf.js, and real-time Socket.IO updates; `audit_vatin.html` renders three anomaly tables (orphan replacements, replaced normals, mismatched tax periods) fetched from `/api/audit-vatin`; `summary_vatin.html` builds Chart.js line charts and a comparison table against `/api/summary`. All pages share shell assets loaded from `/` (`theme.js`, `toast.js`, `export.js`, `sidebar.js`, `utils.js`, `style.css`) and inject a global sidebar via `fetch('/sidebar.html')`. Data flows through REST endpoints (`/api/data-vatin`, `/api/items/vatin/:no_faktur`, `/api/branches`, `/api/me`) plus Socket.IO events (`upload-pdf-vatin-batch`, `request-action-faktur`, `data-baru-vatin`, `upload-batch-selesai`). The `arsip_vatin/` subdirectory is a flat document store of thousands of vendor PDFs named `{batchPrefix}_{NPWP}_{Company}.pdf` grouped by batch prefixes (`20305G_`, `250310_`, `30236G_`, `Berca JO_`, `Perlu Verifikasi_`), consumed as downloadable attachments from the dashboard. There is no backend code in this scope — it is purely the client-facing slice that consumes the server's API.
